One lookup read the whole store

The mail store keeps one record, a binding, for each message in each folder. To find where one pending message came from, the old code read every binding in the store to find one row. It did that once for each pending message, so the time grew with store size times pending messages: a folder with a few hundred pending messages in a store of about 175,000 bindings took 44 s to read instead of 0.4 s.

The current version (v0.12.0) jumps straight to the right row through an index. Press Run to measure both versions here, in this tab. Everything is synthetic; nothing leaves your computer.

Builds stores of 1,000 to 200,000 bindings. Takes about 15 seconds.

Raw numbers

Old is crate commit 8907303; current is 73e2aea (v0.12.0). Both stores use their complete storage migration and initialization SQL, with SQLite 3.54.1, the version the crate bundles. The chart shows the origin lookup; the destination lookup behaves the same way. Each pending message adds two bindings to the size you chose: a tombstone with a settled base in c0 and a pending create in c1. Other bindings share the same source and alternate between present and absent bases. Time is the median of 31 warm runs of one lookup, without prepare and bind. VM steps and full-scan steps are SQLite statement counters, not estimates. “Batch” runs one lookup for every pending message. A zero time means the lookup was faster than the browser's clock can measure; the step counter is still exact.
